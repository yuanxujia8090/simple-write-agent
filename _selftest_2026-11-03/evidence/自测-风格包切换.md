# 一篇稿两种语气：用风格包代替口头约定

## 问题不在提示词，在约定方式

同一个作者往往要写两种完全不同的东西：产品实测需要硬，句子短、结论前置、敢下判断；周记需要软，允许留白、允许不确定。过去的管理方式是每次开工前加一句「今天硬一点」或「今天随意点」。

这句话有三个毛病。

第一，它是口头的，不可复用。写十次要说十次，每次措辞还不一样。

第二，它会衰减。对话一长，早期那句约束被后续内容稀释，模型开始回到默认语气。

第三，它不可验证。你没法回答「这次的语气到底跟上次是不是一套」，只能凭感觉。

风格包解决的就是这件事：把语气从「临时说的话」变成「有路径、有入口文件、可被读取的一份配置」。

## 风格包是什么

形式很简单，一个目录：

```text
~/.writing-agent/styles/<style-id>/
  profile.md        # 优先入口
  SKILL.md          # 没有 profile.md 时用这个
  banned-words.txt  # 可选
  samples/          # 可选样例
```

规则只有一条硬要求：目录里至少要有 `profile.md` 或 `SKILL.md`，工具优先读 `profile.md`。其余文件是可选的，`samples/` 目前不参与解析。

放在用户目录而不是仓库里，是有意的。仓库里只保留 `styles/README.md` 和 `styles/_example/` 两份可公开内容，`.gitignore` 忽略 `styles/*`。私人语气全文不进 git——这样你不会因为一次 `git add .` 把个人风格指南推到远端。

## 两种选包方式

**按 id 选。** id 对应 `~/.writing-agent/styles/<id>/`：

```bash
writing-agent --file ./notes.md --style hardcore --fast
```

**按路径选。** 直接指向任意目录，包不必装在用户目录下：

```bash
writing-agent --style ~/.writing-agent/styles/hardcore
writing-agent --style ./my-style
```

**用环境变量选。** 设 `WRITING_AGENT_STYLE`，适合固定在一台机器上的默认语气。命令行 `--style` 优先级高于环境变量；两者都没有时不报错，也不注入风格，按默认行为走。

判断「这是 id 还是路径」的规则很直白：绝对路径、以 `.` 开头、带 `/` 或 `\` 的，都当路径处理；其余当 id。所以写 `--style ./hardcore` 和 `--style hardcore` 是两件事，前者找当前目录，后者找用户目录。

## 怎么确认选对了

只跑 `--style`、不给素材和话题时，命令只打印启动检查，会明确列出：

- 风格包：id（解析到的根目录）
- 入口：实际读到的是 `profile.md` 还是 `SKILL.md`

这两行很关键。很多人以为风格没生效，其实是 id 解析到了另一个目录。先看这两行，再谈效果。

## 一次失败怎么排查

工具在风格解析上是「失败就报错」，不静默回退到默认风格。这是个好设计：如果它悄悄用默认语气生成，你会以为风格包生效了，实际上一整篇都白写。

常见报错和对应动作：

- **找不到风格包目录**：`~/.writing-agent/styles/<id>` 不存在。要么包没装，要么 id 拼错，要么你以为它是路径但其实被当成 id。按报错里打印的完整路径去 `ls` 一下最快。
- **风格包路径不是目录**：`--style` 指到了一个文件。指向包含入口文件的目录。
- **风格包缺少入口文件**：目录存在，但没有 `profile.md` 也没有 `SKILL.md`。从 `styles/_example/` 复制一份再改。
- **读取风格包失败**：多半是权限或编码问题，入口文件需要 UTF-8。
- **风格 id 不能包含路径分隔或 `..`**：想用目录就传路径，别把路径塞进 id。
- **风格引用不能为空**：`--style` 后面跟了空值，或者环境变量是空字符串。

一条实用顺序：先 `ls` 报错里的路径，再看入口文件名，最后才怀疑风格内容写得不对。

## 从零建一个包

```bash
mkdir -p ~/.writing-agent/styles/demo
cp -R styles/_example/* ~/.writing-agent/styles/demo/
# 编辑 ~/.writing-agent/styles/demo/profile.md
writing-agent --file ./notes.md --style demo --fast
```

`profile.md` 里写什么，直接影响输出。经验上，写「约束」比写「形容词」有效：与其写「语气要专业」，不如写「结论放第一段；每段不超过三句；不用『赋能』『闭环』这类词；数据必须带出处，没有出处就写没有出处」。

形容词是给感觉的，约束是给执行的。工具读的是文本，它只能执行后者。

一份能用的 `profile.md` 大致长这样：

```markdown
# 硬核实测

## 结构
- 第一段给结论，不超过三句
- 第二段给验证方式：命令、参数、看到的结果
- 再给边界与风险

## 句式
- 单段不超过三句
- 不用「赋能」「闭环」这类词

## 事实纪律
- 数据必须能指回来源；没有来源就写「未验证」
```

这份文件不值得写长。写到两屏以上，约束之间开始互相打架，执行时反而容易漏掉关键几条。

## 风格包不负责什么

把边界说清楚，能省掉很多错误期待。

风格包不提供事实。素材里没有的数据、没有的案例，风格再硬也不会出现。它也不会自动学会你的写法——目前不解析 `samples/`，所以不能指望丢几篇旧文进去就完成模仿。

它也不替代选题和大纲。风格包管的是「怎么说」，管不了「说什么」。一篇没有论点的稿子，换成硬派语气只会变得更硬地空洞。

真正能感知到的变化，通常在三个地方：开头不再铺背景而是直接给结论；段落变短，不再一句话套三层从句；该说「没验证」的地方就说「没验证」，而不是用模糊词滑过去。

## 两个包的常见分工

- **硬核实测包**：结论前置、短句、允许直接否定、要求给出验证方式。
- **白话叙事包**：允许长句、允许第一人称、允许不确定表达、禁止堆术语。

两个包不要试图合成一个「全能语气包」。混合的约束会互相抵消，最后得到一个既不够硬也不够软的中间态。分开装，按篇选，切换成本只有一条参数。

## 边界

- 风格包只影响语气与约束，不改变素材内容和事实。素材没写的结论，风格再硬也不会凭空出现。
- `samples/` 目前不解析，别指望放几篇范文就自动模仿。
- 仓库内不提交私人风格全文，这是约定，也是 `.gitignore` 的实际行为；需要团队共享时，用仓外路径 `--style <目录>` 引用。
