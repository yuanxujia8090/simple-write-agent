## 2026-10-29：启动阶段实施取舍

- **工具链最小化**：已按推荐选了 Node 22 ESM + tsx + Vitest + TypeScript 7，参数解析用标准库 `parseArgs`，不引入 commander/yargs 或打包器。原因：本阶段只验证启动链，少一层构建和依赖就少一处和真实运行不一致的地方；后续如果参数变复杂再评估。
- **配置默认值指向本地**：默认 `provider=openai-compatible`、`baseURL=http://localhost:11434/v1`、`modelId` 留空。原因：产品是本地优先，留空比填一个假模型名更诚实，`firstRun` 会提示用户填写；代价是 CLI 概览显示空模型名，属预期。
- **`markerPath` 只表示“实际读到的标记”**：`--cwd` 指向没有标记的目录时返回 `null`，不是“将来要写入的路径”。原因：一个字段只表达一个事实，避免调用方误以为标记已存在；写入路径可由 `MARKER_DIR`/`MARKER_FILE` 重算。
- **确认幂等键**：`(artifactId, artifactHash, confirmationHash, decision)` 四元组作为唯一键。原因：T0 E2 实测同一决策第二次提交能被识别为 `duplicate_confirmation`，且不依赖自增序号；`artifactId` 保证不同产物的相同文字不会互相吞掉确认。
- **文件与数据库边界的对账策略**：主稿先写临时名再 `rename` 到正式路径；崩溃后对账把无 DB 记录的正式文件判为“未登记版本”，要求人工 adopt（登记为 temporary）或 discard（移到 `.discarded`，不删除）。原因：T0 E4 实测这两种选择都能收敛，且满足“不静默采用、不静默覆盖”；直接删除文件会让用户的编辑成果不可恢复。
- **故障注入代替真实杀进程**：E3/E4 用事务内抛错模拟进程在提交前退出。原因：可重复、可断言；限制是没覆盖操作系统层面的断电/强杀，真实崩溃演练放在 T15。
- **锁暂不接入启动流程**：锁实现与测试已完成，但 `writing-agent` 启动时不获取锁。原因：本阶段要求“任何创建用户数据目录的行为只在用户明确启动会话后发生”，会话库尚不存在，提前加锁只会制造空锁文件。

## 2026-10-29：首条闭环实施取舍

- **先内存后 SQLite**：工作流服务先用内存实现，接口按 `WorkflowService` 固定。原因：本阶段要验证的是阶段/门禁/文件衔接，过早引入建表和事务会把两类问题混在一起；代价是进程退出即丢状态，下一阶段必须替换并补表结构契约测试。
- **确认幂等检查放在状态校验之前**：批准后产物已是 `draft`，若先校验“必须 temporary”会把重放误判成非法。原因：重复提交应返回 `duplicate_confirmation` 而不是报错；已由 4 个用例锁住。
- **创作简报暂不设独立确认卡**：固定输入直接生成简报并按临时产物保存。原因：PRD 3.2 要求简报变化后重新确认，但当前没有交互界面，硬加一个脚本门禁会变成第三种确认语义；明确记为未实现，留到交互阶段。
- **导出替换本会话主稿**：默认导出路径就是主稿路径，导出时替换它；指定 `--output-dir` 时仍按不覆盖规则换名。原因：PRD 4.6 的产物结构里主稿与导出同为一个 `<slug>.md`，另存 `-2` 会让用户拿到两份内容不同的“主稿”。
- **文件指纹用落盘内容算**：`recordExport` 记录的是实际文件 hash，不是结构化终稿的 hash。原因：后续外部编辑对账比较的是磁盘内容；两者混用会在接入检测时误判。
- **固定模型结果入库到 `src/agent/fixed-model.ts`**：不在测试里各写一份假数据。原因：重放命令、编排测试、端到端测试共用同一份内容，断言才能对得上。

## 2026-10-30：持久化与文件保护取舍

- **整份会话重写**：每次提交按 `sessionId` 删除派生行再整批插入，不做增量 `UPDATE`。原因：一次确认要改五张表，整份重写让原子性由一条事务直接保证；代价是会话很长时需要改成差异写入，已写进阶段方案的已知边界。
- **业务逻辑只保留一份**：抽出 `WorkflowStore` 端口，内存与 SQLite 共用同一套阶段/门禁规则。原因：复制一份「持久化版业务逻辑」会立刻产生两套语义；169 个既有用例在重构后零改动通过，是最好的回归证据。
- **`fileHash` 与 `contentHash` 分开记**：`contentHash` 对确认卡，`fileHash` 对磁盘文件。原因：两者指纹算的内容不同（结构化内容 vs 落盘文本含换行），混用会在外部编辑检测时误判。
- **外部编辑检测放在终稿门禁之前，而不只在导出前**：实测发现只在导出前检查会出现「批准已提交、阶段已是 exported、文件没写」的不一致。原因：用户确认的是磁盘上那份稿子，稿子变了就不该按旧确认推进。
- **checkpoint 行是重申已有稳定点，不伪造新状态**：事务内写的是提交前已存在的 checkpoint 行，通道值来自保存器自己。原因：伪造通道值会让 LangGraph 读到不存在的图状态；ADR 0012 要的是「恢复点与业务状态同批可见」，不是新造检查点。
- **`checkpoints` 语句延迟 prepare**：只有真的带 checkpoint 调用时才准备 SQL。原因：纯业务测试不装保存器，提前 prepare 会因缺表失败，把测试逼成「必须配图」。

## 2026-10-30：主题与 HTML 渲染取舍

- **用 mdast 而不是正则或第三方 HTML 生成器**：按总体技术方案 §6.6 选 `mdast-util-from-markdown` + GFM 扩展，自写「AST → 内联样式」渲染器。原因：PRD 要求的节点子集与「子集外保留原文并警告」只有在 AST 上才做得干净；正则方案无法区分代码块里的 `#`。
- **主题校验架子比 PRD 字面宽一档**：`lineHeight` 同时接受数字和数字字符串。原因：样例 `archive/my-theme.json` 里是字符串 `"1.7"`，严格按数字校验会把官方样例判成非法；宽一档比改样例安全。
- **非法主题不抛错，只回退 + 警告**：`loadTheme` 永远返回可用主题。原因：主题只是样式，写错主题不该挡住写作和导出；错误信息放在 `warnings` 里由界面展示。
- **HTML 与 Markdown 同 slug、同目录**：重新导出时按 `replacePath` 替换本会话自己的 HTML。原因：与「导出替换本会话主稿」保持一致，避免用户拿到 `-2` 的旁支文件。
- **HTML 失败算部分成功**：Markdown 是主稿，HTML 是派生；写 HTML 失败不能回滚已经落盘的主稿。原因：PRD §4.6 明确要求「保留已生成的 Markdown 并允许单独重试」。

## 2026-10-30：模型适配取舍

- **模型端口一律异步**：`WritingModel` 7 个方法改成返回 Promise。原因：真实模型天然异步，同步签名只能靠阻塞或假同步骗过去；改造后 202 个既有用例零改动通过，说明编排层本来就该这么写。
- **端口与 SDK 分两层**：`ChatPort`（结构化输出 + 流式事件）与 `WritingModel`（7 个阶段）分开，AI SDK 只在 `src/model/ai-sdk.ts` 出现。原因：换 SDK 或加 provider 时不动业务；也便于用假端口跑测试，不联网。
- **配置只从环境变量与 config.json 来，`.env.local` 只是便利入口**：`loadLocalEnvFile` 不覆盖已存在的 shell 变量。原因：临时覆盖（`VAR=x npm run ...`）必须能压过文件，否则调试时会困惑。
- **模型名缺失时不发请求**：直接 `AppError("CONFIG")` 并告诉用户填哪个变量。原因：本地服务在没模型名时会给出很绕的 404，先把可读错误放在自己这层。
- **模型错误不重试**：`generateObject` 失败直接冒泡成 `RunState.error`。原因：重试属于编排策略，应在 T11 的失败处理里统一做；现在偷偷重试会掩盖配置错误，也会让「同一确认卡只能推进一次」的验证变难。
- **`.env.local` 与 `.env` 一起忽略**：两个名字都常见，漏一个就可能把密钥提交上去。
