## 交接目标

交付一个可安装、可类型检查、可运行测试并显示帮助的最小 TypeScript 命令行脚手架；完成最小配置/工作目录解析，并用锁定的实际依赖和故障注入验证暂停恢复与提交一致性。实验结论应决定下一阶段如何实现持久化，不要求本阶段完成写作产品闭环。

## 工作区现状与保护要求

交接时项目已有本轮开发准备文档改动，另有未跟踪 `.pi/`。这些改动可能还没有提交；不要假设基线提交包含它们。

1. 开工先运行 `git status --short`、`git diff`，阅读本 handoff 和开发准备审查，确认工作区中的当前文件。
2. 保留已有所有改动，尤其是根目录 `README.md`、`agents.md`、`CONTEXT.md`、`docs/` 下的决策/计划/需求/审查，以及 `.pi/`。不得用模板或生成器覆盖它们。
3. 只在本交接的允许范围内新增/修改程序文件；更新 `docs/design/`、`docs/adr/`、`docs/changes/` 时保留既有文本并按章节增补。
4. 不运行清理、删除、强制覆盖、数据库迁移、提交、推送或发布操作。遇到需要删除用户数据、覆盖已有用户文件、发布到外部、付费服务或改变需求范围时停止并请求用户确认。
5. 不读取、输出、复制或记录密钥；所有测试使用固定结果和临时目录，不调用真实模型、真实搜索或外部付费服务。

## 执行范围

### 包含

- **T1 最小脚手架**：Node.js + TypeScript 应用入口、包脚本、类型检查、测试、`writing-agent --help`。仅加入这一步实际需要的依赖和目录。
- **T2 最小启动配置**：环境变量与 `~/.writing-agent/config.json` 读取及校验；环境变量覆盖文件配置；凭据缺失给出可读提示。实现 `--cwd` 优先、最近 `.writing-agent/workspace.json` 向上查找、无标记使用当前目录的解析规则及可测试接口。工作目录身份字段须为目录搬移关联会话留位。
- **T2 的可安全验证部分**：用户主目录定位、目录创建行为、文件权限策略和单实例锁方案先写本阶段技术方案；任何会创建用户数据目录或持久化文件的行为必须由用户明确启动对应程序后才发生，不得在安装、测试或模块导入时修改真实用户目录。测试锁时只使用临时目录。
- **T0 机制实验**：用固定结果，不调用模型或搜索，验证下列语义：
  - 生成候选与等待确认分开；恢复暂停后可取得同一候选版本；
  - 重复提交同一确认不产生二次推进；
  - 实际 checkpoint 保存器与业务状态能否共享所需的数据库事务；必须使用锁定版本，并记录具体 API 和实验结果；
  - 在提交各步骤注入失败，检查业务版本、门禁、阶段、Trace 与稳定检查点的一致性；
  - 文件写入与数据库提交之间中断时，恢复过程能确定哪个文件版本有效，且不静默覆盖。
- **阶段文档**：开工前在 `docs/design/` 新建日期命名的实施方案；结论若改变或细化关键架构决策，新增 ADR；完成后补 `docs/changes/` 的实际改动和验证记录，并更新主计划 T0/T1/T2 的实际状态。

### 不包含

- 首条写作闭环、TUI 完整交互、模型调用、真实搜索、文章生成、HTML、完整数据库 schema、备份迁移系统。
- 尚未由实验确认的持久化接口全面铺开。
- 多智能体、向量检索、自动发布、多租户或其他平台。
- 修改已确立的产品行为、删减 MVP 验收条件，或把历史研究建议提升为新决策。

如果本阶段发现启动脚手架无法在不实现大部分产品代码的前提下验证 LangGraph 暂停恢复，应明确报告依赖和阻塞证据，并把 T0 拆为“库级实验”和“后续应用集成实验”；不要伪造端到端结论，也不要扩大阶段范围。

## 实施约束与建议方案

- 推荐 TypeScript + Node.js + Vitest（TypeScript/JavaScript 测试工具）；采用 TDD（Test-Driven Development，先写失败测试再实现），不额外引入第二套 Agent 循环。
- 先检查项目已有主题样例、忽略文件和配置约定；创建文件前确认路径没有用户内容。新增脚手架不要覆盖现有 `README.md`。
- 用纯函数/显式参数实现配置解析与工作目录解析，避免单元测试读取或写入真实主目录。
- 对目录标记、锁文件和配置文件定义明确的权限、损坏文件和并发行为；单实例锁必须在正常退出和异常退出路径验证释放/恢复策略，不能靠陈旧锁永久阻塞用户。
- T0 实验应保持独立、最小且可重复，包含固定输入、注入故障点、预期状态、实际数据库/文件检查和运行命令。SQLite 同文件不等于同事务，文件写入不受数据库事务保护。
- 若实验表明现成保存器不能满足 ADR 0009，先记录可复现事实与候选修正方案；这是已有原子提交要求的具体化，不等于允许悄悄取消该要求。不要在本交接内大规模重写架构。
- 所有运行时配置与凭据不得进入 Trace、日志、测试快照或交接记录。测试数据使用明显虚构值。

## 验收条件

阶段只有在以下结果均有证据，或明确报告阻塞及可复现证据时，才可收尾：

1. 从新检出或当前工作树按文档命令安装/运行后，`writing-agent --help` 可执行且返回预期帮助；具体命令写入运行文档。
2. 类型检查通过；测试输出明确报告通过数量，覆盖配置优先级、配置损坏/缺省、工作目录解析（显式路径、向上认领、无标记）、路径/权限错误与锁行为。
3. 测试和模块导入不触碰真实用户主目录；写入类测试全部使用临时目录，临时文件和锁可回收。
4. 锁定的 LangGraph/checkpoint 依赖版本及实际暂停恢复接口记录在阶段方案/变更记录中。
5. 暂停恢复、重复确认、事务失败注入和文件/数据库边界中断各有可复现命令、预期/实际状态；每项若无法验证，明确写清限制和下一步，不以静态代码阅读替代。
6. 本阶段关键状态不变量明确：只有一次有效确认能推进；失败事务不留下部分业务提交；文件版本与已确认版本不一致时显式阻止或进入对账，不静默覆盖。
7. 主计划只勾选有实际证据通过的 T0/T1/T2 子项；完成或阻塞状态与变更记录一致。T2 未做的完整配置引导、真实配置写入或锁语义不得误标完成。
8. `git diff --check` 通过；最终回复列明改动文件、验证命令和输出、未验证项、阻塞；确认 `.pi/` 和交接时既有文档改动仍保留。
