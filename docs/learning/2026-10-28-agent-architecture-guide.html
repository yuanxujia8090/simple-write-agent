Agent 架构，
先弄清谁决定下一步。

写作像编辑部，客服像服务台。模型负责理解与提议；程序负责权限、状态、预算和交付。架构设计，就是把这些责任分清楚。

面向：熟悉前端、正在学习 Agent 工程的你三个官方公开案例单文件 · 离线可读 · 无外部依赖
先说当前项目：它是单人、本地、公众号长文写作工具。仓库当前以需求、设计、计划为主，实施清单从脚手架起仍待推进。本手册评价的是设计，不宣称写作程序已运行。推荐保留现有主方向：固定阶段流程 + 局部模型决策 + 人工确认。

事实口径：2026-10-28 读取当前仓库与官方资料。案例图是为学习重绘的简化图，不代表商业产品完整内部架构。页面内的演示仅切换说明，不调用真实模型、搜索或业务系统。

01 / 方法

像设计一笔订单，先设计完成条件。

前端不会先挑状态管理库，再决定订单是否能付款。Agent（能根据目标和工具结果选择下一步行动的智能程序）也一样：先定义业务结果，再决定模型参与到什么程度。

目标与验收 → 数据流 → 决策边界 → 工具与权限 → 状态与恢复 → 评测与运行
  1. 定义交付物、禁区和成功标准。写作：交付可编辑主稿和同源网页稿，硬事实有可追溯来源。客服：问题解决或带完整摘要转人工，而不是“回答了一段话”。
  2. 用真实请求拆数据流，不先拆角色。写清每一步拿什么、交什么、失败交给谁。能用代码判断的，不让模型猜。
  3. 选择最少的自主决策。步骤确定，用 Workflow（工作流，程序写好路线）；要根据搜索结果决定查什么，用受限 Agent；只有多个独立子任务值得并行时，再拆多角色。
  4. 给工具写合同，而不是只写函数名。参数、返回值、权限、超时、重复执行后果、成功凭证都要明确。工具返回“成功”也必须有可核对的结果。
  5. 设计过程如何存、失败如何续。区分会话、任务状态、文件版本、执行记录。像支付回调一样，先问“上一次到底成功了吗”，再决定能否重做。
  6. 先用最小样本证明闭环。固定请求、参考结果、评分规则、失败场景和成本记录。先证明比一次模型调用更有用，再增加框架、角色和记忆能力。
I.

单次模型调用

只做明确的分类或提取。输入够、工具不需要动态选择时，最便宜也最容易验收。

II.

固定流程 + 局部 Agent

整体路线稳定，但研究或排错需要临场判断。当前写作项目优先选这个。

III.

多角色协作

拆分能减少上下文干扰或真的能并行。代价是重复研究、交接遗漏、预算与一致性管理。

依据：Anthropic：Building effective agents。它是经典模式资料，原文也提示工具生态已变化；本手册借鉴模式，不把旧接口当最新接口。

客服：先分清“回答”与“办事”

以下是建议的通用设计，不是 OpenAI 教学示例已经具备的能力。客服有三条路径：查知识回答、读取个人业务数据、执行真实业务动作。

渠道接入 → 服务端确认身份与会话 → 意图分流

订单查询

服务端根据当前账号过滤订单 → 只读工具查询 → 模型解释结果。

改签 / 退款

程序校验资格和金额 → 客户确认 → 受控执行 → 查询业务结果。

04 / 当前项目设计检查

不是再加几个角色，
而是把已有承诺变成可执行合同。

已覆盖：阶段流程、两类人工确认、产物版本与指纹、外部编辑检测、研究预算、事实追溯、真实样本评测与安全演练要求。下面区分已有要求待细化、文档冲突待统一和建议新增的实施细节。

先验证 · 落地机制

确认事务如何覆盖检查点与文件？

现状
架构决策要求版本、确认、阶段、执行记录与检查点同事务提交；技术设计同时采用现成 SqliteSaver（LangGraph 的 SQLite 检查点保存器）直接透传。
问题
同一数据库文件不等于同一连接上的一次事务。保存器还涉及异步序列化；文件写入也不受数据库事务自动保护。文档尚未证明这些边界如何接起来。
影响
可能出现数据库已确认旧内容、文件已变新版本，或业务状态已提交但恢复点未同步。
建议
先锁定依赖版本，做最小事务实验：验证保存器能否加入同一提交边界；文件先写独立版本，再提交指向它的元数据，启动时对账。如何实现仍须验证，不在此擅自改既有决策。
验收
在文件写完、业务表更新、保存检查点等位置分别中断；每次恢复都能解释唯一有效版本，旧确认不会批准新稿。

项目证据：技术设计 §4.2、§7.2、§16.4；架构决策 版本化产物与确认原子提交。官方证据：SqliteSaver 构造器、put、putWrites。结论是“需要验证集成”，不是“官方组件不能实现”。

先统一 · 运行语义

暂停、取消、重做究竟停在哪？

现状
技术设计写阶段完成保存，部分章节说取消不写新检查点；需求和计划又写 Ctrl+C 保存检查点并回主界面。执行记录还计划节点结束批量落库。
问题
框架恢复会重跑暂停节点，而不是从那一行继续。哪些代码能重放、取消后哪些结果有效、崩溃前工具事件保存到哪，需要统一。
影响
恢复可能重复生成或写入；批量事件尚未持久化时，恰好丢掉最后一次失败证据。
建议
生成与等待确认分离；给有副作用的动作记录稳定动作编号和结果。定义“取消请求 → 已停止 → 等待恢复”状态；重要动作前后立即记账，流式文字可批量保存。
验收
暂停节点恢复两次、确认按钮重复提交、写完文件后强制退出、模型取消后迟到结果，都不能错误推进阶段或重复覆盖文件。

项目证据：需求 §5.4；技术设计 §4.3、§9.2、§12.2、§15.5；计划“人工门禁与恢复”。官方：暂停与恢复规则。

先细化 · 权限与隐私

本地素材能读，不代表能发到外面。

现状
已有“模型只读”“写入由程序控制”“凭据不进执行记录”和安全演练。需求允许配置外部模型和搜索。
问题
还缺工具级的路径、网络与数据出境规则：允许读哪些目录？链接跳转后能否访问本机服务？搜索词是否可能含私人素材？
影响
网页里的恶意指令可能诱导越权；素材可能经模型请求或搜索词外传，不能仅凭“文件没上传”就判为本地隐私安全。
建议
路径解析后检查真实位置和符号链接；网页读取限制协议、私网地址、跳转、体积与时间。把网页当资料不当命令；外部模型和搜索的发送内容范围要清楚展示并授权。
验收
恶意网页索要本地凭据时工具拒绝；越界路径、符号链接逃逸、跳转本机地址都被拦截；日志与外发内容按规定处理。

项目证据：需求 §3.3、§5.1；技术设计 §9.3、§15.6；计划“安全与故障演练”。这些是已有安全要求的具体化，不要求新增自动发布或云服务。

先补接口 · 上下文

下游节点到底看到哪版稿件？

现状
已有上下文组装顺序、超限裁剪和消息失效。设计说大纲/草稿按需读文件，但写作节点同时配置为没有模型自主工具。
问题
应明确由节点代码预读，而不是期待模型自行取文件。作者档案只在输入阶段注入还是后续重载生效，历史消息是否重复携带素材，也需统一。
影响
可能拿旧稿审查、漏掉最新风格约束，或把重要来源裁掉后继续生成。
建议
逐节点列“输入版本、读取者、必需字段、最大长度、输出”。生成前由程序读取指定大纲或草稿；保护简报、约束、当前版本和必需证据；保护项超限就停，不静默丢弃。
验收
修改大纲再生成、重载作者档案、素材超窗口、旧消息失效四个样例，核对实际模型请求中的版本与内容。

项目证据：技术设计 §15.6、§16.2–§16.4；需求 §3.6.1。可借鉴 官方上下文工程文章。

先明确 · 证据边界

链接能打开，不等于支撑这句话。

现状
现有规则刻意只验证来源可追溯性；逐句语义核查已明确排除在最小可用版本之外。这不是遗漏。
问题
来源存在、资料内容、结论真伪是三件事。仅保存一个网址，不足以让作者快速判断当时依据；把未核实事实改成“我觉得”也不自动消除误导。
影响
文章可能引用了真实页面，却得出页面没有支持的结论；快速模式可能只换语气而保留错误断言。
建议
在现有素材快照上关联声明、原文摘录、位置与稿件版本；清楚标注“可追溯”而非“事实已证实”。快速模式优先删除无证据的具体断言或交人工处理，不凭空改成作者经历。
验收
用“网址真实但内容无关”“来源互相冲突”“无法读取原文”三个样例，作者能看到依据和限制。自动逐句真伪判定仍后置，不扩大范围。

项目证据：需求 §3.6.2；事实核查边界决策。建议属于证据呈现与契约细化；若要强制自动语义核查，需要另行确认范围。

已有要求 · 变成样本

让评测从“要做”变成“可以重复跑”。

现状
计划已要求真实写作样本、人工参考与规则、基线、失败案例、成本和延迟，不能再把“缺评测”当新发现。
问题
还需选定实际样本、评分口径、版本记录和可接受界限。用户批准率只说明接受情况，不等于事实正确。
影响
更换模型或提示词后无法判断进步还是退步；单篇顺畅演示可能掩盖常见失败。
建议
先选 6–10 个小样本，覆盖纯观点、资料写作、来源冲突、私人素材、外部编辑和中断。比较“一次模型直接写”与完整流程，记录人工修改量、证据缺口、总耗时与调用用量。
验收
同一组输入能重复评估；结构与权限规则自动检查，内容由作者按清晰标准评审；不能用模型自评分数替代人工参考。

项目证据：计划 §7 真实样本评估、真实模型验证；官方：Agent 评测方法。6–10 是本项目起步建议，不是行业统一标准。

实施前核对 · 预算与版本

别把“最多三步”当“最多三次请求”。

现状
研究轮数、搜索次数与节点工具步数已分开。设计仍使用 maxSteps 等历史接口写法；超时重试与结构重试还有嵌套空间。
问题
一步可能请求多个工具；失败重试和框架重放又会放大调用量。当前官方 AI SDK 文档用 stopWhen 配合步数条件控制循环，不能把旧示例直接当最新可执行代码。
影响
以为有限预算，实际搜索、读取、模型调用和等待时间仍可能超出预期。
建议
锁定实际版本；在模型适配层映射循环停止接口。工具执行前计数，并建立全会话模型调用、读取量、耗时、用量上限；给基础设施失败与结构失败各自明确总尝试次数。
验收
一步发出多个工具调用、恢复时预算重建、错误重试、取消后迟到结果四种情况，都能守住统一上限。

项目证据：技术设计 §15.2–§15.4；官方：工具调用与循环停止文档。目前没有安装版本，结论是“实现前核对”，不是既有代码已出兼容故障。

落地首轮 · 简化与运维

先做能证明架构的小路径。

现状
计划开头主张最小闭环，但任务仍主要按脚手架、存储、工具、流程、界面分波；备份、恢复与日志隐私已有验收要求。
问题
如果每层先建全，就会很晚才看到真实文章；“SQLite 被占用即另一实例”的表述，也不能代替明确的单实例锁方案。
影响
学习停留在目录和接口；恢复与运维问题拖到最后才暴露。
建议
从本地素材 → 简报 → 论点确认 → 草稿 → 审查 → Markdown 导出做薄路径，再加恢复与外部编辑；首轮就明确单实例锁、备份范围、日志保留和升级失败恢复。
验收
真实短文运行、一次取消恢复、一次外部编辑保护、一次备份恢复有可复核证据。按既有范围逐步补齐，不删减已确认功能。

项目证据：计划 §1.1、§6、§7；以可验证闭环推进的决策。

这次不建议增加：多智能体、向量数据库、长期自动记忆、云端多租户、自动发布。当前证据不足以支持这些成本；优先落实已有范围。以上是分析建议，不是对产品技术路线的新批准。
05 / 学习与验证

换一个故障，看你是否真的分清责任。

像前端请求超时：页面没有收到响应，不代表服务端没有写入。Agent 工具也如此。重试之前，先问动作是否有副作用、结果能否核实。

小演练：动作做完了，进程却退出。

先对账文件与版本，再决定是否重做。

用动作编号、文件路径和内容指纹核实：它是已提交稿件、未提交候选，还是用户后来编辑的文件？数据库未记完成时，不能直接覆盖重写。

责任：文件层报告真实内容；状态层决定版本；流程层决定重做哪一步。

推荐的实施顺序

  1. 先做两个小实验：暂停节点重放；确认与检查点提交边界。
  2. 再跑薄闭环：本地素材到短文，显式传递版本与来源。
  3. 最后扩展：搜索、外部编辑、终端交互、网页导出和完整样本评测。

这里是建议，不在本次任务中实施写作程序。

用三句话自检

为什么写作项目不先拆成五个 Agent？

阶段稳定；独立角色并非必要；跨角色交接会增加信息损失与成本。先用程序控制阶段，研究局部动态选择工具。

恢复时有检查点，为什么还要查文件？

检查点保存流程状态；文件写入不随数据库事务自动回滚。恢复必须核对实际产物和版本，不能只相信“上次停在研究阶段”。

客服说“退款成功”，怎样才算成功？

通过服务端按当前账号授权，取得真实业务系统已完成记录。模型文本只是解释，不是到账或执行凭证。
