## 一、先给一个总比喻

把整个写作 Agent 想成**一家只有一个员工的写作工作室**：

- **员工（Agent）** 负责跑腿：研究、起草、自查。它很能干，但**没有判断力**——所有"要不要""好不好"都得问你。
- **你（用户）** 是主编，只在关键节点拍板：论点选哪个、大纲行不行、稿子能不能发。
- **档案室（SQLite 数据库）** 记下工作室的一切：做过什么、到哪一步了、被拒过哪些版本。
- **工作台（工作目录）** 摆着你能亲手改的东西：大纲文件、草稿文件。

这套系统设计的全部核心，就是一件事：**让员工跑腿、你拍板、档案室记账、工作台能改**，四者各司其职。

## 二、系统怎么分层（从外到内）

想象一栋楼，每一层只认识下面一层：

```
┌─────────────────────────────────┐
│  顶楼：界面层（你看到/操作的）      │   ← 终端 TUI（将来可换成图形界面 GUI）
├─────────────────────────────────┤
│  中层：Agent 流程（"员工"）        │   ← LangGraph 编排的写作流程
├─────────────────────────────────┤
│  底层：能力库（工具人）            │   ← 模型/搜索/文件/数据库
├─────────────────────────────────┤
│  地窖：纯逻辑（规则书）            │   ← 领域规则（阶段、回退、事实、预算）
└─────────────────────────────────┘
```

**关键规矩：楼层之间只准从上往下打招呼，不许下面回头管上面。** 界面层不存业务状态——它只是一块"玻璃"，看到什么就展示什么、你点什么就往上递什么。将来换图形界面，只换顶楼，底下不用动。

为什么要这样？因为**你最终要封装成 GUI**（需求第 4 点）。现在把界面层设计成"可整体更换"，到时候就是把终端那层拆掉、装上图形那层，其他全复用。

## 三、最核心的一个设计：员工怎么"停下等你拍板"

这是整套系统最关键、也最容易被搞砸的地方。用一个场景讲：

你启动 `writing-agent`，Agent 开始研究、生成论点。这时它写了 4 个论点候选，需要你选一个——**但代码是顺序往下执行的，你不可能在它跑的时候插话**。怎么办？

我们的做法是三层配合：

```
你 ──► 界面层 ──► Agent流程 ──► 能力库（模型）
        ▲
        │  ① 流程跑到"等确认"这个点，暂停自己
        │  ② 发一条消息给界面："请用户选一个论点"
        ▼
        │  ③ 界面画出确认卡，等你按键
        │  ④ 你选了"第 3 个"，界面把答案回传给流程
        │  ⑤ 流程从刚才停下的地方继续
        └──
```

用术语说：流程通过 **interrupt（暂停）** 停住，等你通过 **resume（恢复）** 给出答案，再从暂停点继续。中间的"对话"全靠一条**事件通道**（EventPort）传递消息。

**为什么值得专门设计？** 因为：
1. 流程**不能**自己瞎猜你选哪个——写作方向必须你定；
2. 界面**不能**只负责显示——它要能随时把决定传回给流程；
3. 将来 GUI 只要换一种"传话的方式"（从终端改成网络/进程间），流程完全不用动。

## 四、界面层（TUI）具体有哪些"玻璃窗"

| 界面 | 干什么 | 对应需求 |
|---|---|---|
| 欢迎页 | 新建 / 恢复 / 退出；提示本目录有 N 个未完成会话 | 任意目录启动 |
| 进度显示 | 当前阶段、已耗时、"正在研究/正在写第 2 章…" | 长流程可见（Q4） |
| 确认卡 | 论点/大纲/事实报告/终稿 的"确认 / 编辑 / 拒绝"三选 | 4 个内容门禁 |
| 素材采纳列表 | Agent 搜到的资料，整批确认 | 采纳门禁 |
| 外部编辑提示 | "检测到你改了草稿，重审吗？" | 中间产物可改 |
| 会话列表 | 未完成会话，含最近事件 | /list |
| Trace 查看器 | 回放这次写作从头到尾都发生了什么 | 可追踪 |
| /note /idea | 随手记想法 / 跨会话灵感速记 | Q4/Q5 |

这些窗格**不存状态**——它们像电视屏幕，显示的是"档案室 + 流程"传上来的内容。

## 五、数据放哪（两块，别混）

```
档案室（全局）  ~/.writing-agent/        ← 电脑级别，跟着用户走
    config.json         配置
    profile.db          作者档案（风格/禁忌/身份）
    session.db          所有会话、到哪一步、被拒版本、Trace、想法
    materials/会话ID/    素材快照

工作台（工作目录）  你启动的目录/          ← 项目级别，跟着文章走
    .writing-agent/     该目录的身份标记
    outlines/xxx.md     大纲（你可直接打开改）
    articles/xxx.md      草稿主稿
    articles/xxx.html    排版后的文章
```

**为什么分两处？**
- 档案室管"这台电脑上你所有的写作"，跟你在哪个文件夹启动无关；
- 工作台管"这篇文章的文件"，是你想亲手碰的东西；
- 你在任意目录启动 → 向上找身份标记 → 认领回这个工作台 → 接到档案室里对应的会话。

一句口诀：**档案室记账，工作台放货。**

## 六、四个关键环节怎么转（白话时序）

**1. 主流程（到草稿为止）**
```
输入话题 → 检查信息够不够
  └ 不够 → 访谈 5 问 → 确认简报
→ 生成 3-5 个论点 → 你选 1 个
→ 生成大纲 → 落到 outlines/ → 你确认
→ 生成草稿（流式，边生成边显示）→ 落到 articles/
```
全程你只出手 2–3 次，之后就能看到草稿——这就是"快速到稿"（需求 Q3）。

**2. 门禁（每个"你拍板"的点）**
```
流程跑到门禁 → 暂停 → 界面弹确认卡 → 你选
  → 拒绝：保留原稿 + 记下你的修改意见 → 退回上一阶段重做
```

**3. 外部编辑检测（Q1 场景）**
```
你直接打开草稿改了 → 下次流程要读它之前 → 比对内容指纹（哈希）
  → 变了 → 停下问："采用新稿重审 / 忽略 / 重新生成？" → 绝不偷偷覆盖
```

**4. Ctrl+C（不是杀死，是存档）**
```
按 Ctrl+C → 取消当前动作 → 已完成的阶段已存档 → 回到主界面
  → 下次 /resume 从最近稳定点继续，进行到一半的整个阶段重做（不把半成品当成果）
```

## 七、几个选型，用大白话讲为什么这么选

| 部件 | 选了 | 为什么 |
|---|---|---|
| 数据库驱动 | better-sqlite3 | 快、稳、官方就支持存"暂停点"；是同步的，好写 |
| Markdown 转 HTML | unified（抽象语法树） | 把稿子拆成一棵"结构树"，能精确给每段套样式、也能在这棵树上做事实核查——一树两用 |
| 流程↔界面传话 | 内存事件通道 | 单进程够用；将来换 GUI 时把"传话方式"换成网络/进程间即可 |
| 模型调用 | Vercel AI SDK | 统一封装各家本地/云端模型 |

（技术理由的详细对比在专业版第 6 节。）

## 八、性能：为什么不会"折腾一下午"（需求 Q3）

花时间的只有一件事：**本地模型写字**。其余（存库、转格式、画界面）都是毫秒级。

模型写字：2000–5000 字约需 2–8 分钟（看机器）。所以把时间花刀用在四处：

1. **流式显示**——字是蹦出来的，你能立刻看到它开始写；
2. **研究有预算**——最多研究 2 轮，不无限搜（Q2）；
3. **`--fast` 只留 2 个门禁**——最快捷径到终稿；
4. **不反复重写**——只有结构不对才重来（最多 2 次），不因"写得不够好"循环重生成（好坏你来定，模型不自评）。

到稿路径上你只出手 2–3 次，其余时间看着它写。

## 九、将来要扩展（GUI、自动记忆…）怎么接

- **GUI**：只换顶楼界面层 + 把"传话方式"从终端换成网络——底下全复用；
- **作者自动记忆**：现在每步都记 Trace（流水账），将来从这些流水账里自动提炼"你反复拒绝什么、喜欢什么语气"，写进作者档案；
- **新搜索/新模型**：在能力库加一个新"插头"即可。

一句话：**这次把接缝都留好了，将来都是加零件，不是拆房子。**

---

## 十、一句话总结

这套系统 = **员工跑腿（Agent）+ 主编拍板（门禁）+ 档案室记账（SQLite）+ 工作台放货（工作目录）**，用一条"事件通道"把四者串起来；界面是可换的壳，规则是稳定的芯，扩展都发生在插头处。
